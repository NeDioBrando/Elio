## Part 1 - Check-UI — Clean Roblox UI Design System & Implementation Skill

### 1. Skill Overview & Purpose

**Check-UI** is the definitive design system standard for modern Roblox cartoon, simulator, and tycoon games (inspired by top-tier titles like Pet Simulator 99, Anime Champions, and Blade Ball).

This skill equips any AI agent or human developer with the exact mathematical proportions, color formulas, component architectures, Luau implementations, and responsive scaling mechanisms required to produce pixel-perfect, cohesive, and non-generic Roblox interfaces.

### Core Tenets (Non-Negotiable Rules)
1. **Zero AI Slop / Generic Looks**: Every frame must have intentional cartoon depth, high-contrast borders, pastel highlight strokes, and tactile micro-interactions.
2. **Strict Typography**: Every title, label, counter, button, and text box **must** use `Enum.Font.GothamBlack` with black outline `UIStroke` (thickness proportional to font size: 2.0px to 3.5px).
3. **Solid Canvas (`#3b5866`)**: Never make window backgrounds semi-transparent. Always use solid slate blue `Color3.fromRGB(59, 88, 102)` with `UICorner` (4px) and outer `UIStroke` (3.5px, `#181e22`).
4. **Signature 3D Beveled Square Close Button `[X]`**: Exact 38x38px square with a dark burgundy bottom bevel extrusion (`#730010`), shifted face with vibrant crimson/pink gradient (`#ff7daf` to `#ff1428`), inner pastel stroke highlight, GothamBlack "X", and centered `UIScale`.
5. **2-Tier 3D Header Shadow Divider**: Every header must end with a 2-line separator: an upper 3px dark thematic accent bar + a lower 3px solid black bar.
6. **Seamless Checkerboard (Damier) Fade**: Full-height texture overlay (`rbxassetid://385956923`) with a vertical `UIGradient` transparency sequence (`1 -> 0.82 -> 0.35 -> 0.10`) to eliminate hard cutoff lines.
7. **Aspect Ratio Preservation**: Icons must **never** be stretched. Always set `ScaleType = Enum.ScaleType.Fit`.
8. **Universal Responsive Scaling**: All modal windows and HUDs must be governed by dynamic `UIScale` responsive calculations based on `camera.ViewportSize` (baseline `1050 x 620`, clamped `[0.52, 1.18]`).
9. **Center-Anchored Interactions**: ALL hover, click, and scale animations MUST originate from the exact geometric center via `AnchorPoint = Vector2.new(0.5, 0.5)` + child `UIScale`.
10. **The 5 Canonical Menu Archetypes**: All game interfaces should follow one of the 5 canonical specifications: Shop, Codes, Rebirth, Settings, or Daily Rewards.
11. **Iconless Button Mandate**: Whenever a button WITHOUT an icon is requested (Throw, Action, Jump, Redeem, Confirm, etc.), it MUST ALWAYS strictly follow the Studio-Verified Canonical Standard: sharp 90° rectangular geometry (no UICorner), 3px solid `#0C141A` outer border, 90° color gradient, black checkerboard overlay (`0.91 -> 0.62` fade), TRIPLE glass specular inner highlight frames (`InnerHighlight1`, `2`, `3`), and centered GothamBlack white text with 3px `#11171A` contextual stroke & 1px optical offset.

### 4. Multi-Device Responsive Scaling Engine

```lua
local camera = workspace.CurrentCamera

local function getDeviceScale()
    local viewport = camera.ViewportSize
    if viewport.X <= 0 or viewport.Y <= 0 then return 1 end
    -- Baseline resolution: 1050 x 620
    local scaleX = viewport.X / 1050
    local scaleY = viewport.Y / 620
    local factor = math.min(scaleX, scaleY)
    -- Clamped between 0.52 (smartphones) and 1.18 (desktop)
    return math.clamp(factor, 0.52, 1.18)
end

local function updateAllDeviceScales()
    local currentScale = getDeviceScale()
    for _, gui in ipairs(playerGui:GetChildren()) do
        if gui:IsA("ScreenGui") then
            for _, frame in ipairs(gui:GetChildren()) do
                local sc = frame:FindFirstChild("WindowScale")
                if sc and sc:IsA("UIScale") and frame.Visible then
                    sc.Scale = currentScale
                end
            end
        end
    end
end

camera:GetPropertyChangedSignal("ViewportSize"):Connect(updateAllDeviceScales)
```

## Part 2 - Check-Code (Roblox Luau standard)

Check-Code is the code counterpart of Check-UI. Each rule is short, testable and has a reason.
A piece of code is done only when every rule is PASS or NOT APPLICABLE, and every rule that could not be
checked is written down as UNVERIFIED.

### The gate

1. Read the change, file by file. For each file, go through rules 1 to 18 in order.
2. Write the Check-Code table (format below). Each row: rule, PASS / FAIL / WARN / NOT APPLICABLE / UNVERIFIED,
   and the file and line that shows it.
3. If `check_code.py` can run (see below), run it on the changed files and copy its table into your report.
   Its results count. Do not argue with a FAIL from the scanner. Fix it, or explain why the rule does not apply.
4. Fix every FAIL and run the table again. A change with any FAIL is not done.
5. WARN items are not blockers, but each one must be fixed or named in the report with a reason.
6. Where the project has `ul-luau-code` gates (rojo build, lune test, selene, stylua), run those too.
7. In Studio, when the tools are present: run the change with `execute_luau` only if it is safe (no DataStore
   writes, no reward changes), then read `get_console_output` after a `start_stop_play` run. Report what it showed.

### The rules

1. **Server owns state.** Any change to health, currency, score, inventory, rewards, spawning or purchases is
   decided on the server. A client value is a request, never a fact.
2. **Every remote handler validates.** Check, in order: type, range, ownership, then cooldown or distance.
   Only after all four does the server act.
3. **No deprecated globals.** Use `task.wait`, `task.spawn`, `task.delay`. Never `wait()`, `spawn()`, `delay()`.
   Use `os.clock()` for timing in new code, not `tick()`.
4. **Every `WaitForChild` has a timeout** and handles `nil`. A wait with no timeout can hang forever.
5. **Every lookup is nil-checked** before it is indexed: `FindFirstChild`, `GetService` on a fallible name,
   DataStore reads, `Players:GetPlayerFromCharacter`, any value that can be `nil`.
6. **Every connection has an owner.** Each `:Connect` is stored and disconnected when its owner ends, or the
   code says why it lives forever (for example, a server-wide `PlayerAdded`). See the `lifecycle-cleanup` skill.
7. **No hidden loops.** Every `while true do` has a `task.wait` in it, a way to stop, and a stop when its owner ends.
8. **No per-frame waste.** Code in `Heartbeat`, `PreSimulation`, `PostSimulation` or `RenderStepped` does no
   allocation of tables or closures, no `GetService` or `FindFirstChild` lookups, and no whole-world scans.
   Cache them outside the loop.
9. **DataStore is safe.** Read-modify-write uses `UpdateAsync`, not `GetAsync` then `SetAsync`. Every call is in
   `pcall` with retry and backoff. A failed load never writes defaults over real data.
10. **Remotes match at every end.** Each remote name is defined once (the Net module). The sender, the server
    handler and the receiver use the same argument count and types.
11. **Tunables live in Config.** Balance numbers (prices, health, speeds, timers, spawn rates, sizes) come from a
    Config table. A number in a service body is a FAIL unless it is a structural constant, such as an index or a
    pixel offset, and the code says so.
12. **Every `pcall` reports its error.** `pcall` that discards the error is a FAIL. Capture it and `warn` it, or
    return it to the caller.
13. **Pure logic is pure.** Calculations live in Core modules that take plain numbers and tables, with no
    Instance, service or remote calls, so they can be tested without Studio.
14. **Typed where it counts.** New modules use `--!strict` when the project allows it. Remote payloads and shared
    data shapes have an `export type`. Casts with `::` have a comment saying why they are safe.
15. **No invented APIs.** Every Roblox or Luau call in the change has a line in the API table with its docs page
    and signature, or is marked `-- UNVERIFIED: <API name>`. Memory is not a source.
16. **Clients do not write server state.** A client script never sets a server-owned attribute, value, or
    position that changes gameplay. Attributes that the server sets are read-only on the client by convention.
17. **Effects cannot break gameplay.** Visual and sound code is wrapped so its failure cannot stop a gameplay path.
18. **No leftovers.** No `print` debugging, no commented-out code, no unused locals, no globals created by
    accident. Selene and the scanner check these; a human checks the rest.

### API table (part of the report)

| API | Docs page read | Signature used | Side (server / client / both) |
|---|---|---|---|

Any row missing a docs page is UNVERIFIED, and every use of it is marked in the code.

### Table format

| # | Rule | Result | Where (file:line) | Note |
|---|---|---|---|---|
| 1 | Server owns state | PASS | Services/Reward.luau:12 | |

### What the scanner can and cannot do

`check_code.py` is a pattern scanner. It finds rule 3 (deprecated globals), rule 4 (WaitForChild with no timeout),
rule 5 (indexing a `FindFirstChild` result on the same line), rule 7 (`while true` with no wait nearby), rule 9
(`GetAsync` and `SetAsync` in one file), rule 12 (`pcall` with no capture), rule 18 (`print`, unused-looking
leftovers, `tick()`), and rule 14 (missing `--!strict`). It does not parse Luau, so it cannot prove rules 1, 2, 6,
8, 10, 11, 13, 15, 16 or 17. Those need a human or the model reading the code, and the table must say so.
A scanner PASS does not mean the code works. Say "passes Check-Code scan" and nothing more.

## Skill: server-authority
Use when: any feature where a player's action changes game state (damage, purchases, scoring, spawning, inventory, rewards).

The server owns the game. Clients own the display (input, camera, UI, effects).
- Every value that arrives from a client is a request. Check, in this order: type, then
  range, then ownership, then distance or cooldown. Only after all four is it a fact.
- Never trust a client's score, health, currency or position for a reward.
- Movement is the one common exception: fast first-person movement is often client-side.
  If you do that, keep the consequences (score, elimination, rewards) on the server.

## Skill: docs-lookup
Use when: any Roblox API, property, event, method, enum or service you are not certain of, or any question about what Roblox currently does.

Fetch the page before any code depends on it.
- Fetch with fetch_roblox_doc. Class and enum reference: create.roblox.com/docs/reference/engine/classes/<ClassName>.
  Luau pages: create.roblox.com/docs/luau. If the exact path is unknown, fetch the section
  index and follow the link.
- Only create.roblox.com and developer.roblox.com addresses can be fetched.
- If a page fails to load, the API is unverified. Say so and ask the user to paste it.
- Record in the plan: the page URL, the exact signature, argument and return types, and
  whether it runs on the server, the client, or both.
- If the page and your memory disagree, the page wins, and you say so.

## Skill: remote-events
Use when: code that sends data between client and server, or a remote that fires but nothing happens.

A remote payload has three ends: the sender, the server handler, and the receiver.
- If you change the arguments at one end, check the other two. A mismatch fails silently.
- Use plain RemoteEvents for gameplay. Keep the names in the Net module.
- When a remote seems to do nothing, check in this order: the name matches on both
  sides; the server listens before the client fires; the arguments match in count and type;
  the server handler's validation is not rejecting the request.

## Skill: roblox-gotchas
Use when: writing Luau for Roblox, or reviewing code for bugs before the user runs it.

- Use task.wait, task.spawn and task.delay. Do not use wait(), spawn() or delay().
- ScaleTo is a Model method. A MeshPart scales by setting .Size.
- WaitForChild with no timeout can block forever. Always pass a timeout.
- A bare pcall hides the error. Capture the message and warn it.
- A method and a cache field with the same name can return the wrong value. Keep names distinct.
- A grounded Humanoid stops scripted velocity. Setting WalkSpeed to 0 is itself a brake.
- A custom animation at Idle priority or above overrides the default walk, run, jump and
  fall on every joint it poses. Author it at Core, or test walking, running, jumping and
  landing with it playing.
- A weapon or any object welded to a body part is checked attached to a character in
  motion, not only in the tool it was made in.
- Any check that cannot find its target must fail. "Not found" is a failure, not a pass.
- Cosmetic effects must never break gameplay. Wrap them in pcall and let them fail quietly.

## Skill: review-for-exploits
Use when: reviewing code or finishing a feature that touches remotes, rewards or Toolbox assets.

Read the code as an attacker would. For each remote handler, ask:
- Can a client call this with values I did not expect (nil, a huge number, a wrong type)?
- Can a client call it too often (no cooldown, no rate limit)?
- Can a client call it for another player's object (no ownership check)?
- Does a success message reach the client before the server has checked?
For each Toolbox asset: has every Script and ModuleScript inside it been read, and is each
one needed?
List what you found, fix it, and say which of these you could not rule out by reading.

## Skill: datastore-safety
Use when: saving or loading player data, leaderboards, inventories or any DataStore use.

Player data is the most expensive thing to lose. Protect it first.
- Use UpdateAsync for read-modify-write. Never read, change, then SetAsync: two servers
  can overwrite each other.
- Wrap every DataStore call in pcall. On failure, retry with backoff (a short wait that
  doubles each attempt, with a fixed maximum number of tries).
- If a load fails, do not write defaults back. Keep the session in a read-only state or
  block saves until the load succeeds. Overwriting real data with defaults is the worst bug.
- Save on meaningful events (purchase, level up, leave, server shutdown via BindToClose),
  not on every change. Batch small changes in memory.
- Keep keys versioned (for example "PlayerData_v2") so a schema change does not read bad data.
- Say in the report which DataStore calls were checked by reading and which need a
  Studio test with real data.

## Skill: client-ui-safety
Use when: building or changing any UI, HUD, menu or client-side display.

The client shows state. The server decides it.
- Never let a UI value decide gameplay: a button sends a request, the server answers.
- Always pass a timeout to WaitForChild on PlayerGui and on any UI child you depend on,
  and handle the case where it returns nil.
- Connect events to Instances that are guaranteed to exist. Disconnect connections when
  the UI is destroyed, or they pile up on respawn.
- Do not read text or numbers back from UI labels to compute anything. Keep the value in
  a Lua variable and update the label from it.
- Respect ScreenGui.ResetOnSpawn and check it on every respawn, so the UI rebuilds
  correctly rather than leaving stale state.

## Skill: luau-accuracy
Use when: writing or reviewing any Luau code that calls a Roblox or Luau API.

Hallucinated code is the most common failure. Prevent it before it is written.
- Every API call in the code must map to a line in a fetched docs page. Keep a short
  table in the plan: API, page read, signature, side (server, client or both).
- Common mistakes to check against the page, not memory: wrong argument order, a method
  called with a dot instead of a colon (and the reverse), a property that is read-only,
  a property name that is close to a real one but not the same, and an event that
  does not exist on that class.
- Luau is not Lua 5.1. Use Luau syntax: type annotations are optional, compound
  assignment (+=) is valid, and string interpolation is not built in (use string.format
  or ..). Check any standard library function you are not sure of.
- Check return types. Many calls return nil on failure (FindFirstChild, GetService on a
  bad name, DataStore reads). Handle nil before indexing.
- If you cannot find a function on a docs page after two tries, do not replace it with
  a plausible one. Report it as unverified and stop that line.
- Mark any line you could not verify with a comment: -- UNVERIFIED: <API name>. Do not
  ship it silently.

## Skill: luau-performance
Use when: a task touches a per-frame loop, a Heartbeat or other tick, a large loop over world objects, any code that runs for every player, or the user reports lag, stutter or low FPS.

Write the code so the hot path does the least work per frame.
- Cache services and frequently used Instances once, at module top:
    local Players = game:GetService("Players")
  Do not call GetService, FindFirstChild or WaitForChild inside a loop that runs every frame.
- Cache a lookup result in a table keyed by the Instance. Look up once, reuse many times.
- Use CollectionService tags (GetTagged, GetInstanceAddedSignal, GetInstanceRemovedSignal)
  instead of GetDescendants() or a whole-workspace scan that runs repeatedly.
- Do not scan the world every frame. Scan once when something changes, then update the set.
- Avoid allocations in per-frame code: no new tables, closures, strings built with ..,
  or Vector3 and CFrame objects created inside a loop that could reuse a value.
- Build a string from many parts with table.concat on a table, not with .. in a loop.
- Use table.create(n) when the size is known, and table.move to copy slices.
- Use table.freeze on read-only config tables, so a bug that writes to them fails loudly.
- Pick the right event: RunService.Heartbeat or PreSimulation for per-frame logic, and a
  Changed or signal event for "when something changes". A while-true loop with a wait is
  the slowest choice and rarely needed.
- A large number of identical parts is a Model with a Union or a MeshPart, or a
  Terrain/ParticleEmitter setup, not thousands of separate Scripts. Count the Instances
  before and after the change.
- Batch remote traffic. Send one message with a list, not one message per item, and never
  fire a remote every frame when a state change is enough.
- State in the report: what was on the hot path, what you removed, and what you measured
  with luau-profiling. If you did not measure, say the change should help, not that it does.

## Skill: lifecycle-cleanup
Use when: any code that creates connections, tasks, Instances or UI for a character, round, match, player or tool that later ends.

Everything created for something that ends must be released when it ends.
- Keep a single cleanup list per owner: connections, spawned tasks, temporary Instances.
  Release all of them in one function. A Janitor or Maid style module is a good fit when
  the project already has one. Check the project before adding a new one.
- Disconnect every signal connection you created. Destroying an Instance does not
  disconnect connections made to other objects, so do this explicitly.
- Cancel a task you started with task.delay or task.spawn when its owner ends, by keeping
  the thread handle and calling task.cancel on it.
- Respawn is the common leak. Connections made on CharacterAdded must be removed on the
  character's Died or AncestryChanged, or they stack up on every respawn.
- Remove the players table entries on PlayerRemoving, after the data save is complete.
- Test the cleanup path, not only the happy path: a player who leaves mid-round, a round
  that ends while a timer runs, a tool that is dropped mid-use.
- In the report, say which connections and tasks are released where, and which you could
  not confirm by reading.

## Skill: api-watchlist
Use when: any task that uses one of the APIs listed below, or the first Luau code written in a session.

These APIs are used often. Their exact names, arguments and return types are the
most likely places for a mistake, so they follow a stricter rule.
- Before the first use of any API below in a task, fetch its docs page with fetch_roblox_doc
  and quote the signature in the plan. Do not write it from memory, even if it looks familiar.
- The list (fetch and confirm each one you use):
  task.spawn, task.defer, task.delay, task.wait, task.cancel, task.desynchronize, task.synchronize

## Skill: check-ui-rules
Use when: EVERY UI task, no exceptions: any screen, button, window, HUD or style change.

Name: Check-Clean-UI

Description: Ultra-complete Design System and implementation skill for creating production-grade, cartoon/simulator UI in Roblox Studio (Check-UI standard).

Method: Strictly use Enum.Font.GothamBlack for all text, applying a black outline UIStroke proportional to the font size (2.0px to 3.5px).
Construct all window canvas backgrounds using a solid, opaque slate blue (Color3.fromRGB(59, 88, 102)) with a 4px UICorner and a 3.5px outer UIStroke.
Build close buttons as an exact 38x38px square featuring a dark burgundy bottom bevel, a crimson/pink gradient face, an inner pastel stroke highlight, and a centered UIScale.
Implement a 2-tier 3D shadow divider at the bottom of every header, consisting of an upper 3px dark thematic bar and a lower 3px solid black bar.
Apply a full-height checkerboard texture overlay (rbxassetid://385956923) that fades seamlessly using a vertical UIGradient transparency sequence of 1 -> 0.82 -> 0.35 -> 0.10.
Use dynamic UIScale responsive calculations based on camera.ViewportSize, clamping the factor between 0.52 and 1.18 for all modal windows and HUDs.
Set AnchorPoint = Vector2.new(0.5, 0.5) with a child UIScale on ALL interactive elements so hover, click, and scale animations originate from the exact geometric center.
Base all game interfaces on one of the 5 canonical menu archetypes: Shop, Codes, Rebirth, Settings, or Daily Rewards.
Create iconless buttons using sharp 90° rectangular geometry without UICorners, implementing a 3px solid #0C141A outer border, a black checkerboard overlay, and triple glass specular inner highlight frames.

Pitfalls & Corrections: Pitfall: Creating generic-looking UI or using semi-transparent window backgrounds. Correction: Never make window backgrounds semi-transparent; always use a solid #3b5866 canvas with intentional cartoon depth, high-contrast borders, and pastel highlight strokes.
Pitfall: Icons becoming stretched and losing aspect ratio. Correction: Icons must never be stretched; always enforce ScaleType = Enum.ScaleType.Fit.
Pitfall: Leaving hard cutoff lines on the checkerboard overlay. Correction: Apply a vertical UIGradient transparency sequence to eliminate hard cutoff lines and create a seamless damier fade.
Pitfall: Animations scaling unevenly or from the wrong origin point. Correction: Guarantee all hover and scale interactions originate from the center by ensuring the AnchorPoint is strictly set to Vector2.new(0.5, 0.5).
Pitfall: Rounding the corners of standard iconless buttons. Correction: Iconless buttons must strictly follow the canonical standard of sharp 90° geometry with no UICorner applied.

Verification Checks: Font: ALL text uses Enum.Font.GothamBlack — no exceptions.
Canvas: Window background is solid #3B5866 with BackgroundTransparency = 0.

## Skill: expert-gui
Use when: any Roblox interface: architecture, layout, performance, input, responsiveness.

Architecture
- The UI reads state and sends requests. The server decides game state (see the server line in
  check-cycle). Keep UI code in a client Controller and layout code in pure modules where possible.
- One ScreenGui per window or HUD. Set ResetOnSpawn on purpose: false for a persistent HUD, and
  rebuild the parts that must survive respawn.
- Build a screen once and show or hide it with Visible or Enabled. Do not destroy and rebuild
  it on every open.
- Render lists from data. Keep one hidden template, clone it for each item, and update only the
  items whose data changed. Remove the rest.
- Listen to changes (GetAttributeChangedSignal, remote events) instead of polling in a loop.
  Never update text or positions every frame unless the thing really moves each frame.
- Disconnect connections when a screen closes, and destroy what it created.

Performance
- Every GuiObject costs. Use fewer, larger elements. Do not build a 500-cell grid as 500
  hand-made frames when a UIGridLayout does it.
- ClipsDescendants and AutomaticSize cost more on large lists. Use them only where the layout needs them.
- Put decorative UIStroke and UIGradient on a template, not on every item of a long list.
- Use ImageRectOffset and ImageRectSize for sprite sheets, not many images.
- Tween a few things at a time. Keep tweens short. Cancel a tween before starting a new one on the same object.
- Keep ZIndex stable. Changing ZIndex across a big tree forces re-sorting.

Layout
- Use UIListLayout, UIGridLayout and UIPadding. Do not hand-place repeated items.
- Size with UIScale for whole windows (see check-ui-standard for the clamp), UISizeConstraint for
  a range, and UIAspectRatioConstraint for icons and cards.
- Labels: TextScaled with UITextSizeConstraint, or AutomaticSize where the text sets the size.
- Touch targets: keep buttons at least 44 px on a phone. Leave 8 px or more between targets.
- Test at phone portrait, phone landscape and a PC window. Test with 0 items, 1 item and many items.

Input and access
- Buttons respond to Activated, which covers mouse, touch and gamepad.
- Make every button reachable by gamepad: Selectable = true, in a sensible order.
- Show a clear pressed state and a disabled state. Do not rely on hover.
- Respect the top bar and safe areas.

Anti-patterns to reject
- Creating GUI inside a loop without a template. wait() or spawn() (use task.*). Hard-coded
  pixel positions for everything. Changing text every frame. Duplicate ScreenGuis for one
  window. Client-side prices or rewards shown as final before the server confirms.

## Skill: gui-syntax
Use when: every GUI script, before it is marked done. Example: references/gui-syntax/example.lua.

Roblox-valid GUI code. These rules come from Roblox's API dump.
- Create with Instance.new("ClassName"). Set properties, then Parent last.
- Text lives on TextButton and TextLabel. ImageButton and ImageLabel have no Text or Font.
- Clicks: Activated (mouse, touch and gamepad). MouseButton1Click is mouse and touch only.
- Enums in full and spelled exactly: Enum.Font.GothamBlack, Enum.ApplyStrokeMode.Border,
  Enum.ScaleType.Fit, Enum.ZIndexBehavior.Sibling.
- A ScreenGui from a LocalScript goes under PlayerGui: screen.Parent = player:WaitForChild("PlayerGui").
- UDim2.new takes four numbers. UDim.new takes two. Color3.fromRGB takes 0 to 255. Color3.new
  takes 0 to 1. Vector2.new takes two.
- Transparency is 0 to 1. ColorSequence and NumberSequence keypoints run from 0 to 1, in order,
  starting at 0 and ending at 1.
- Image properties take "rbxassetid://<id>". Icons use ScaleType.Fit. Repeating textures use ScaleType.Tile.
- UICorner.CornerRadius = UDim.new(0, pixels). UIGradient.Color is a ColorSequence.
  UIGradient.Transparency is a NumberSequence.
The user can run check_gui_syntax.py on the script. It checks class names, property names, events,
enum values and argument counts for variables made with Instance.new in the same file. It does not
catch undefined variables, and a pass does not prove the code runs.

## Skill: vfx-and-animation
Use when: any visual effect, particle, trail, beam, highlight, tween, animation, camera shake, screen flash, UI transition or feedback effect.

Effects make a game feel good. They are cosmetic and must never decide gameplay.
- Effects are client-side. The server sends the event (what happened, where). Each client draws the
  effect. Do not replicate a particle or tween through a remote every frame.
- Keep effects cheap. Use a small pool of effect Instances, reuse them, and hide or disable them
  instead of creating and destroying them on every hit. Use Debris for one-off effects that must go.
- Limit the count: a fixed maximum number of live effects per type. Drop the oldest, or skip the new.
- Tweens: TweenService:Create(instance, TweenInfo.new(time, Enum.EasingStyle.<style>,
  Enum.EasingDirection.<direction>), goal). Cancel a tween before you start another on the same object.
  Keep most tweens under about one second. Use the same easing for the same kind of motion across the game.
- Animation: load animations through the Animator (an AnimationController's Animator or a Humanoid's
  Animator) with LoadAnimation. Set the track's priority on purpose, and stop tracks you no longer need.
  Check that a custom animation does not override the default walk, run, jump and fall unless that is
  the goal (see roblox-gotchas).
- Particles: use a ParticleEmitter with Emit(count) for bursts. Use Enabled for continuous effects,
  and turn it off when the effect is out of view or the object is hidden.
- Trails and beams: Trail and Beam need two Attachments. Clean them up with the object they follow.
- Highlight outlines: a Highlight can outline a model. Limit how many are on screen at once.
- Camera shake and screen flash: do them on the client only. Keep them short, and restore the camera
  and any overlay state when the effect ends, and on respawn.
- UI feedback: scale or fade a button on press with a short tween, and keep the pressed state visible
  without hover. Respect the reduce-motion idea: keep effects short and avoid strong flashing.
- Check the cost: count the effects and the instances an effect adds, and measure with luau-profiling
  when a change touches a per-frame or per-hit path.
- Verify the APIs for every effect class and enum you use (fetch_roblox_doc), and mark any you could not
  confirm with -- UNVERIFIED: <API name>.
- In the report, say what was checked by reading, and what needs a screen capture or a play test to judge.

- ul-vfx-library (skill, skills/ul-vfx-library/SKILL.md): Harvest free Creator Store VFX packs, which you have taken into your own Roblox account, into your own searchable library of portable JSON particle recipes by reading every emitter property out of Studio, then classify, find, curate and emit them as a Luau runtime module (VFXKit) that builds them on any part with scale and tint. No effects ship with this skill, only the tooling. Verified by phase-frozen edit-mode screenshots, never by a metric. Use whenever the user wants a Roblox particle effect, explosion, aura, hit effect, fire, smoke, sparks or magic effect found and wired rather than dragged in by hand, wants to build a reusable VFX library from packs they own, or asks why their ParticleEmitter is invisible, never stops, or looks nothing like it did in the pack they copied it from.
